# Ascerex Website Style Rules

**Mode:** First-time full scan (small project, 7 tracked TypeScript/JavaScript source files)

**Baseline fingerprint:** `dee39df1af6c9d83472053f4f74f9aebf586f7af`

These rules preserve the current Next.js component architecture while carrying
forward the visual hierarchy and interaction intent of `../website/`. They do
not authorize copying legacy defects, placeholders, or technical overclaims.

## Golden Files

- `src/app/page.tsx` — route-level content remains data-driven and composes
  shared components; the route stays a Server Component when it does not need
  browser state.
- `src/app/layout.tsx` — global providers, metadata defaults, favicons, and
  global style imports live at the application boundary.
- `src/components/Header.tsx` — browser interaction is isolated in a focused
  Client Component and shared navigation is defined once.
- `src/components/HeroSection.tsx` — repeated visual regions use typed props
  and explicit media variants rather than loosely shaped objects.
- `../website/mission.html` and `../website/assets/css/style.css` — reference
  for Mission-page hierarchy, dark visual language, system diagrams, and
  responsive intent. Translate the intent into React semantics and CSS Modules;
  do not copy fixed-position diagram defects or imperative DOM scripting.

## Naming & State-Control Rules

- Use PascalCase for components and component prop types; use camelCase for
  variables, handlers, and data fields.
- Keep App Router `page.tsx` files server-rendered by default. Add `"use client"`
  only to the smallest component that owns interaction or browser APIs.
- Model repeated content as typed arrays and render it with stable semantic
  identifiers rather than array indexes.
- Keep local interaction state local. Do not introduce Context or an external
  store for page-local selections or disclosures.
- Prefer semantic native elements before adding ARIA roles.
- Use CSS Modules for route- or component-specific presentation. Reserve
  `globals.css` for design tokens, reset/base rules, and global styles.
- Preserve the static site's dark palette, fine borders, uppercase labels,
  measured spacing, and responsive content hierarchy while improving keyboard,
  focus, reduced-motion, and screen-reader behavior.
- Keep SVG geometry and its labels in a shared responsive coordinate system.
  Replace dense diagrams with an equivalent linear layout when the viewport
  can no longer preserve their meaning.
- Treat future capabilities and approval work as future-facing. Models and
  simulations produce conditional evidence, not physical validation.
- Import order: React/Next APIs, third-party libraries, project components/data,
  then the local CSS Module.

## DONTs

- Do not migrate placeholders or unqualified pass/fail, validated, safe,
  certified, proven, or flight-ready claims.
- Do not expose private requirements, raw engineering records, rankings, or
  unpublished evidence in public source files.
- Do not move a whole route to the client because one section is interactive.
- Do not recreate the legacy `querySelector` and manual mutation architecture.
- Do not use clickable `div` or `span` elements or hover-only disclosure.
- Do not place large page-specific style blocks in `globals.css`.
- Do not preserve a diagram whose labels disconnect from its SVG at small sizes.
- Do not duplicate canonical private facts; publish only approved wording.

### 2026-09-09 Style Evolution Log

- Mission-page diagrams preserve their relationship structure on wide screens
  and deliberately become linear, readable sequences on narrow screens.
- Policy categories are keyboard-operable buttons backed by React state; the
  route remains a Server Component.
- Legacy claims about validation, certification, and approval speed are revised
  to describe intended processes and current analytical work accurately.
