# Ascerex Website Style Rules

**Mode:** First-time full scan (small project, 7 tracked TypeScript/JavaScript source files)

**Baseline fingerprint:** `dee39df1af6c9d83472053f4f74f9aebf586f7af`

These rules preserve the current Next.js component architecture while carrying
forward the visual hierarchy and interaction intent of `../website/`. They do
not authorize copying legacy defects, placeholders, or technical overclaims.

## Golden Files

- `src/app/page.tsx` — route-level content remains data-driven and composes
  shared components; the route itself stays a Server Component when it does not
  require browser state.
- `src/app/layout.tsx` — global providers, metadata defaults, favicons, and
  global style imports live at the application boundary.
- `src/components/Header.tsx` — browser interaction is isolated in a focused
  Client Component and shared navigation is defined once.
- `src/components/HeroSection.tsx` — repeated visual regions use typed props and
  explicit media variants rather than loosely shaped objects.
- `../website/vehicle.html` and `../website/assets/css/style.css` — reference for
  vehicle-page information hierarchy, spacing, dark visual language, and
  responsive intent. Translate into React semantics and CSS Modules; do not
  copy imperative DOM structure or global selectors blindly.

## Naming & State-Control Rules

- Use PascalCase for components and component prop types; use camelCase for
  variables, handlers, and data fields.
- Keep App Router `page.tsx` files server-rendered by default. Add `"use client"`
  only to the smallest component that owns interaction or browser APIs.
- Model repeated content as typed arrays and render it with stable semantic
  identifiers rather than array indexes.
- Keep local interaction state local. Do not introduce Context or an external
  store for page-local carousels, selections, or disclosures.
- Prefer semantic native elements (`section`, `button`, `details`, `summary`,
  headings, lists) before adding ARIA roles.
- Use CSS Modules for route- or component-specific presentation. Reserve
  `globals.css` for design tokens, reset/base rules, and genuinely global styles.
- Preserve the static site's dark palette, fine borders, uppercase labels,
  measured spacing, and responsive content hierarchy while improving keyboard,
  focus, reduced-motion, and screen-reader behavior.
- Treat public technical status as typed content. Every demonstrative item must
  carry an explicit visible label; evidence-backed status language must name its
  gate and scope.
- Import order: React/Next APIs, third-party libraries, project components/data,
  then the local CSS Module.
- Component file order: imports, types/constants, component, small local helpers.

## DONTs

- Do not migrate Lorem ipsum, fictional analysis, or unqualified pass/fail,
  validated, safe, certified, proven, or flight-ready claims.
- Do not expose private requirements, raw engineering records, rankings, or
  unpublished evidence in public source files.
- Do not treat manufacturer/directory claims, UI cards, or renderings as
  Ascerex validation.
- Do not move a whole route to the client merely because one widget is
  interactive.
- Do not recreate the legacy `querySelector`/manual text mutation architecture;
  render UI from React state and typed data.
- Do not use clickable `div`/`span` elements or hover-only disclosure.
- Do not place large page-specific style blocks in `globals.css`.
- Do not abstract one-off sections prematurely; extract only verified repeated
  structures or interaction boundaries.
- Do not duplicate canonical private facts. Link to their owner in internal
  migration documentation and publish only approved wording.

### 2026-09-01 Style Evolution Log

- The propulsion gallery confirms that legacy interaction behavior is part of
  the design contract: centered edge peeks, transparent navigation fields,
  hover advance, scroll snapping, selectable square cards, animated corner
  markers, text scrambling, and connected expanding details should persist
  when the underlying content is rewritten.
- Preserve those behaviors in focused React Client Components with explicit
  timer and listener cleanup. Do not replace them with generic carousel chrome
  or decorative gradients.

### 2026-09-08 Style Evolution Log

- Alternate route concepts belong in clearly named, non-indexed comparison
  routes until the preferred direction is approved. Do not replace the active
  route during visual exploration.
- Vehicle storytelling should lead with the program objective and the system
  being developed. Put evidence boundaries close to technical facts without
  turning the page into a wall of caveats or exposing private engineering
  results.
- Prefer cinematic media, editorial typography, technical rules, and a single
  restrained status accent over generic feature-card grids. Motion must carry
  state or hierarchy and respect reduced-motion preferences.
- Keep long-form Vehicle sections within a near-black tonal range. Use adjacent
  charcoal surfaces and fine rules for hierarchy instead of alternating pure
  white and black fields that produce uncomfortable glare.
- During route comparison, shared interactive work belongs in focused
  components so the approved carousel can move into the selected page without
  duplicating its state or timing logic.
- Do not use chart-like decoration unless the geometry communicates a value a
  visitor can understand. Responsive stacking must preserve comparison meaning;
  otherwise use a compact editorial sequence.
- Vehicle-page identity leads with “The Orbiter.” Supporting thesis language
  can be expressive, but internal generation markers stay out of general-public
  presentation until multiple generations need to be distinguished.
